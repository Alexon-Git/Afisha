# Database migrations and safe upgrades

All commands are run from the `backend/` directory. The application no longer
creates tables or changes columns at import time. Alembic owns schema changes.

## First-time installation (empty database only)

1. Copy `env.example` to `.env` for SQLite/local development or use
   `env.compose.example` for Docker/PostgreSQL.
2. **Replace all placeholders** with strong, unique secrets. Do not commit .env.
3. Install requirements: `pip install -r requirements.txt`.
4. Apply migrations: `alembic upgrade head`.
5. Create administrator: `python create_admin.py`.
6. Start API: `uvicorn app.main:app --host 127.0.0.1 --port 8039 --no-proxy-headers`.

Docker Compose waits for PostgreSQL health and runs migration before app start.
If migration fails, the backend will NOT start; investigate before retrying.

## Existing Afisha database (data preservation)

**Never run `alembic stamp` or `downgrade` blindly.**

1. Stop write traffic; take and verify a full backup (e.g., `pg_dump -Fc`
   for PostgreSQL or a consistent SQLite file backup).
2. Restore backup to a separate staging database. Do not experiment in production.
3. Inspect `users`, `categories`, and `events`, including columns, types,
   indexes, uniqueness, foreign keys, row counts and the existing `category`
   and `category_id` fields. Some old startup scripts added columns ad hoc.
4. Compare restored schema with `alembic/versions/0001_initial.py`.
   If equivalent, `alembic stamp 0001_initial` can establish a baseline
   **on the tested restored copy**; then `alembic upgrade head`.
   If schemas differ, write and test an explicit compatibility migration
   instead of stamping a mismatched schema.
5. Verify old record counts, events, images, admin login and API before
   planning a production cutover. Back up again immediately before cutover.

The initial migration intentionally fails if it sees existing application
tables without Alembic history. It does not delete or modify them.

To compare with models after baseline, use `alembic check` in a test
database. Review any reported differences rather than automatically applying
an autogenerated migration.

## Login rate-limit counters (`0002_login_attempts`)

This revision only adds `login_attempts` and its expiry index. It does not
change user records or JWTs. Test `0001_initial` → `0002_login_attempts` on
an isolated copy before deploying. Do not stamp over the new revision:
without its table, login deliberately returns HTTP 503 rather than running
without shared limits. Every worker must use the same database and SECRET_KEY.

Defaults: 5 failed attempts per exact username and 30 per connection peer in
900 seconds, configured by `LOGIN_ACCOUNT_LIMIT`, `LOGIN_SOURCE_LIMIT` and
`LOGIN_WINDOW_SECONDS`. A slot is reserved atomically before password checking;
an interrupted attempt stays counted, a success refunds only its own slot.
Previous failures remain until the original window expires. HTTP 429 carries
remaining seconds in `Retry-After`; attempts blocked by the limiter do not
extend the window. Store failures return HTTP 503 with `Retry-After: 60`.

Expired HMAC counter keys are removed in batches of up to 100 per login request;
without new logins expired rows can remain stored. They contain no plaintext
username, IP, password or token. Successful zero-count rows expire normally.
Multi-host installations require synchronized clocks. SQLite 3.35+ is required
for RETURNING; PostgreSQL 17 remains the intended production database.

Application-level trust of all forwarded headers has been removed. Supported
launchers (`start.py`, Dockerfile, Compose) explicitly disable Uvicorn's own
proxy-header processing. Custom launches must also use `--no-proxy-headers`;
do not set up wildcard forwarded trust. Behind a reverse proxy, clients share
the proxy's source budget until a separate, validated proxy policy is configured.

### Verification performed (2026-11-12)

- SQLite: full suite, 68 tests passed (Python 3.11).
- PostgreSQL 17: `upgrade head`, `downgrade -1`, `upgrade head` succeed;
  `users` is untouched. Parallel requests: 50 for one account admitted exactly 5
  (limit 5), 80 for one source admitted exactly 30; 120 mixed requests produced
  no errors or deadlocks. An unreachable database yields a fail-closed error.
- Docker Compose (isolated project, throwaway database): image builds, `command`
  in compose overrides the Dockerfile `CMD` and still contains
  `--no-proxy-headers`; migrations apply; 5 failures then HTTP 429 with
  `Retry-After`; forged `X-Forwarded-For`, `X-Real-IP` and `Forwarded` do not
  change the source bucket.
- Not verified: migration of a copy of a real legacy database (none available).

### Running behind Nginx (required before public launch)

With `--no-proxy-headers` every client behind Nginx shares one source budget:
in a real Nginx test one client's 31 failed logins caused HTTP 429 for a
different client. A tested safe policy:

- Start Uvicorn with `--proxy-headers --forwarded-allow-ips=<Nginx address>`.
  List only the proxy address; never `*`. Make the value configuration, not a
  hard-coded address.
- Nginx must overwrite, not append, the client's header:
  `proxy_set_header X-Forwarded-For $remote_addr;`
- The backend port must not be reachable from the internet; a direct request
  from an untrusted peer ignores forwarded headers (verified: three forged
  addresses produced one bucket).
- With this setup two client containers got independent source buckets, and
  forged `X-Forwarded-For` from one client did not affect the other.
- If a CDN or load balancer is placed before Nginx, configure Nginx `real_ip`
  for it; otherwise all users again share one address.

The account budget (5 failures per username per 15 minutes) lets anyone who can
reach `/auth/login` lock out a known username for the window. This is a known
limitation; additional protection of the admin login must be in place before
public launch.

The ASGI scheme also remains the transport scheme: verify HTTPS redirects when
configuring the real proxy. The old seeding launcher `run_seed.py` is not a
supported production entry point.

Database migrations and this task's tests must never use the production database.

## Test commands

Install `pip install -r requirements-dev.txt`, then run `pytest -q`
from the `backend/` directory. Tests use isolated temporary SQLite files
and NEVER use the production database.

## Rules

- New schema changes must be new Alembic revisions.
- No schema modifications, test-event seeding or password printing on app import.
- Do not downgrade production without explicit rollback and backup plan.
- Never commit .env, database dumps, or admin credentials.
