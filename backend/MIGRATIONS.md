# Database migrations and safe upgrades

All commands are run from the `backend/` directory. The application no longer
creates tables or changes columns at import time. Alembic owns schema changes.

## First-time installation (empty database only)

1. Copy `env.example` to `.env` for SQLite/local development or use
   `env.compose.example` for Docker/PostgreSQL.
2. **Replace all placeholders** with strong, unique secrets. Do not commit .env.
3. Install requirements: `pip install -r requirements.txt`.
4. Apply migrations: `alembic upgrade head`.
5. Create administrator: `python create_admin.py`.
6. Start API: `uvicorn app.main:app --host 127.0.0.1 --port 8039 --no-proxy-headers`.

Docker Compose waits for PostgreSQL health and runs migration before app start.
If migration fails, the backend will NOT start; investigate before retrying.

## Existing Afisha database (data preservation)

**Never run `alembic stamp` or `downgrade` blindly.**

1. Stop write traffic; take and verify a full backup (e.g., `pg_dump -Fc`
   for PostgreSQL or a consistent SQLite file backup).
2. Restore backup to a separate staging database. Do not experiment in production.
3. Inspect `users`, `categories`, and `events`, including columns, types,
   indexes, uniqueness, foreign keys, row counts and the existing `category`
   and `category_id` fields. Some old startup scripts added columns ad hoc.
4. Compare restored schema with `alembic/versions/0001_initial.py`.
   If equivalent, `alembic stamp 0001_initial` can establish a baseline
   **on the tested restored copy**; then `alembic upgrade head`.
   If schemas differ, write and test an explicit compatibility migration
   instead of stamping a mismatched schema.
5. Verify old record counts, events, images, admin login and API before
   planning a production cutover. Back up again immediately before cutover.

The initial migration intentionally fails if it sees existing application
tables without Alembic history. It does not delete or modify them.

To compare with models after baseline, use `alembic check` in a test
database. Review any reported differences rather than automatically applying
an autogenerated migration.

## Login rate-limit counters (`0002_login_attempts`)

This revision only adds `login_attempts` and its expiry index. It does not
change user records or JWTs. Test `0001_initial` → `0002_login_attempts` on
an isolated copy before deploying. Do not stamp over the new revision:
without its table, login deliberately returns HTTP 503 rather than running
without shared limits. Every worker must use the same database and SECRET_KEY.

Defaults: 5 failed attempts per exact username and 30 per connection peer in
900 seconds, configured by `LOGIN_ACCOUNT_LIMIT`, `LOGIN_SOURCE_LIMIT` and
`LOGIN_WINDOW_SECONDS`. A slot is reserved atomically before password checking;
an interrupted attempt stays counted, a success refunds only its own slot.
Previous failures remain until the original window expires. HTTP 429 carries
remaining seconds in `Retry-After`; attempts blocked by the limiter do not
extend the window. Store failures return HTTP 503 with `Retry-After: 60`.

Expired HMAC counter keys are removed in batches of up to 100 per login request;
without new logins expired rows can remain stored. They contain no plaintext
username, IP, password or token. Successful zero-count rows expire normally.
Multi-host installations require synchronized clocks. SQLite 3.35+ is required
for RETURNING; PostgreSQL 17 remains the intended production database.

Application-level trust of all forwarded headers has been removed. Supported
launchers (`start.py`, Dockerfile, Compose) explicitly disable Uvicorn's own
proxy-header processing. Custom launches must also use `--no-proxy-headers`;
do not set up wildcard forwarded trust. Behind a reverse proxy, clients share
the proxy's source budget until a separate, validated proxy policy is configured.

### Running behind Nginx (required before public launch)

With `--no-proxy-headers` every client behind Nginx shares one source budget:
in a real Nginx test one client's 31 failed logins caused HTTP 429 for a
different client. A tested safe policy:

- Start Uvicorn with `--proxy-headers --forwarded-allow-ips=<Nginx address>`.
  List only the proxy address; never `*`. Make the value configuration, not a
  hard-coded address.
- Nginx must overwrite, not append, the client's header:
  `proxy_set_header X-Forwarded-For $remote_addr;`
- The backend port must not be reachable from the internet; a direct request
  from an untrusted peer ignores forwarded headers (verified: three forged
  addresses produced one bucket).
- With this setup two client containers got independent source buckets, and
  forged `X-Forwarded-For` from one client did not affect the other.
- If a CDN or load balancer is placed before Nginx, configure Nginx `real_ip`
  for it; otherwise all users again share one address.

The account budget (5 failures per username per 15 minutes) lets anyone who can
reach `/auth/login` lock out a known username for the window. This is a known
limitation; additional protection of the admin login must be in place before
public launch.

The ASGI scheme also remains the transport scheme: verify HTTPS redirects when
configuring the real proxy. The old seeding launcher `run_seed.py` is not a
supported production entry point.

Database migrations and this task's tests must never use the production database.

## Organizers and event metadata (`0003_event_metadata`, PR-6)

Based on `0002_login_attempts`. Adds `organizers` and nullable event fields
`organizer_id`, `event_url`, `source`, `verified_at`. The indexed organizer FK
uses `ON DELETE SET NULL`; deleting an organizer never cascades event deletion.
ORM deletion also clears references on SQLite connections without FK enforcement.
Organizer timestamps have server creation defaults; `updated_at` is updated by
ORM writes (direct SQL writers must maintain it themselves).

Two independent VARCHAR/CHECK statuses are non-null with safe server defaults:
`publication_status = draft | published | archived` (default draft), and
`event_status = scheduled | cancelled | postponed` (default scheduled).
Existing events receive draft/scheduled and NULL editorial metadata. No old
events are published, no verification dates are invented, no payment URLs
are copied, and no existing datetime values/types/timezones are altered.
PostgreSQL uses additive ALTER TABLE; SQLite uses batch table recreation,
preserving existing columns/data, indexes and foreign keys.

**Do not release PR-6 alone to production.** Until PR-7 adds visibility and
publication rules, the public API still returns drafts for compatibility.
Ordinary POST/PUT rejects status and verification fields. Organizer contacts
are not exposed automatically; public disclosure needs a controlled action.

Verification (2026-11-15): SQLite full backend suite 296 passed; PostgreSQL
17.11 in a separate disposable Compose project verified fresh 0001→0002→0003,
upgrade of populated 0002, legacy users/categories/events/counters preservation,
defaults, FK/CHECK constraints, model/schema equivalence and ORM/service writes.
Only synthetic data were available; a restored production/legacy database has
NOT been verified. Follow the existing backup/staging/baseline procedure above.

To reproduce PostgreSQL checks, supply ONLY an isolated test database URL:

```bash
AFISHA_PR6_TEST_DATABASE_URL='postgresql+psycopg2://test_user:test_password@127.0.0.1:TEST_PORT/test_db' \
  python -m pytest -q tests/test_event_metadata_migration.py
```

Each PostgreSQL test creates and drops its own randomly named `pr6_*` schema;
the test database role needs schema creation privileges. Without this variable
the same tests use temporary SQLite files. Never supply a production URL.

**Destructive downgrade:** 0003→0002 removes all organizers, organizer links,
event_url/source/verified_at and both statuses. Downgrade cannot reconstruct
those values. It must not run on real data without a verified backup and an
explicit rollback/export plan. No downgrade of real data was performed.

## Test commands

Install `pip install -r requirements-dev.txt`, then run `pytest -q`
from the `backend/` directory. Tests use isolated temporary SQLite files
and NEVER use the production database.

## Rules

- New schema changes must be new Alembic revisions.
- No schema modifications, test-event seeding or password printing on app import.
- Do not downgrade production without explicit rollback and backup plan.
- Never commit .env, database dumps, or admin credentials.


## PR-8: абсолютное время, 0004_event_datetime_utc (2026-11-23)

Владелец подтвердил запуск на новой пустой PostgreSQL 17 и отсутствие старой БД
Afisha с мероприятиями для сохранения (D-021). Черновик перенесён в активную цепочку
0001 → 0002 → 0003 → **0004_event_datetime_utc** совместно с aware API/ORM/фильтрами.

На PostgreSQL миграция берёт ACCESS EXCLUSIVE lock с lock_timeout=5s, проверяет
пустоту events и ожидаемый naive тип, затем меняет datetime на timestamptz через
явный `AT TIME ZONE 'UTC'`. Это DDL для пустой таблицы, **не** интерпретация истории.
При наличии любой строки upgrade отказывает; ревизия 0003, данные и тип сохраняются.
Offline SQL запрещён: проверка пустоты должна быть реальной и под блокировкой.
Другие таблицы/временные поля не меняются. SQLite берёт BEGIN IMMEDIATE и тоже
отказывает при непустой events; физический SQLite DATETIME остаётся прежним,
новый ORM хранит только UTC-компоненты и восстанавливает aware UTC.

Не удалять старые строки/volumes и не stamp 0004 ради обхода отказа. Если вопреки
ожидаемому обнаружены мероприятия — остановиться и отдельно согласовать их данные.
Даже пустота проверенной preview-БД не разрешает менять её без отдельной задачи.

API datetime: `2026-11-12T12:00:00+07:00` → `2026-11-12T05:00:00Z`.
Naive/числовые timestamps → 422. Календарные date/date_from/date_to трактуются
в Asia/Novosibirsk; date_to включителен посредством следующей местной полуночи.
**Downgrade запрещён** до отдельного backup/export и плана временной семантики;
автоматическое удаление зоны не реализовано.

Тесты `tests/test_event_time_contract.py`: чистая 0001→0003→0004, повтор upgrade,
сохранность users/categories/индекса/metadata, отказ populated upgrade без изменений,
HTTP CRUD/verify/publication/status/фильтры/сортировка при четырёх process/session TZ.
Для PostgreSQL используется только отдельный тестовый URL AFISHA_PR8_TEST_DATABASE_URL
(host pr8db либо 127.0.0.1, database afisha_pr8, user pr8_test), новые случайные схемы.
Тесты не удаляют БД/volumes. CI поднимает собственный PostgreSQL17 service и запускает
PostgreSQL-половину матрицы; обычный SQLite suite её пропускает без opt-in URL.
Ранее подготовленный focused checker сохранён в migration_drafts/check_empty_migration.py,
теперь проверяет активную цепочку. Аудит и история: ../docs/audits/PR8_TIME_DATA_AUDIT.md.


## PR-14A.1: импортная схема, 0005_import_schema (2026-11-23)

Одна аддитивная revision после 0004: import_sources/import_runs/event_candidates/
import_candidate_matches. Существующие таблицы/строки не меняются; seed отсутствует.
Статусы pending_review/queued/pending/suggested по умолчанию; записи кандидатов
не создают и не публикуют Event. Проверены populated 0004 → head, повторный upgrade,
ORM/metadata, FK/unique/CHECK и удаление Event с сохранением импортной истории.
Новый циклический FK run.recheck_candidate_id добавляется после обеих новых таблиц
на PostgreSQL; SQLite использует inline FK. Триггеры на двух новых таблицах ставят
candidate.lost_event_link при SET NULL; Event и Organizer не имеют новых триггеров.

Изолированные синтетические проверки:
`AFISHA_PR14_TEST_DATABASE_URL=... python -m pytest -q tests/test_import_schema.py -k postgresql`.
URL допускает только localhost с тестовой парой afisha_pr14/pr14_test либо
CI afisha_pr8/pr8_test; каждый прогон работает в своём случайном pr14_* schema.
Без opt-in PostgreSQL skipped; SQLite запускается всегда с FK enforcement.
Нельзя передавать production URL. Тестовый schema удаляется, volumes не удаляются.

Downgrade удаляет все четыре таблицы и импортную историю. Старые Event/Organizer
сохраняются, но реальный rollback требует отдельного backup/export и плана.
Не применять migration или downgrade к production в рамках этой задачи.


### P2 review PR #30: SQLite runtime FK enforcement

Стандартный SQLite engine приложения включает `PRAGMA foreign_keys=ON` на каждом
новом DBAPI-подключении. Это необходимо для SET NULL и флага lost_event_link при
удалении Event. PostgreSQL и DDL 0005 не меняются. Регрессионный тест использует
обычные engine/SessionLocal в отдельном процессе с DATABASE_URL временной БД,
без test-only FK listener; проверяет ORM/SQL DELETE и новые подключения пула.
