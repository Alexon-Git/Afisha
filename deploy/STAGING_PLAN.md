## Выполненная согласованная очистка

После диагностики пользователь явно разрешил удалить кэш скачанных пакетов APT
и архивные journal старше 7 суток. Выполнены `apt-get clean` и
`journalctl --vacuum-time=7d`, без принудительной ротации активных журналов.
Стандартный APT clean убрал также регенерируемый package cache:
весь `/var/cache/apt` уменьшился с ~176 MiB до 20 KiB.
Journal уменьшился с 216 до 56 MiB (удалено 160 MiB архивов).
Свободное место по df: 2,057,203,712 → 2,409,365,504 bytes (+335.85 MiB),
занятость 80% → 76% (округлённо 2.0 → 2.3 GiB свободно).

После очистки все 9 рабочих контейнеров запущены, DB/Redis healthy;
7 images и 8 volumes сохранены, размеры каталогов backups прежние.
Данные БД/uploads и backups не удалялись, контейнеры не перезапускались.
Полные пользовательские диалоги ботов сейчас не проверялись.

## Границы дальнейшей очистки — требуется отдельное согласие

- Согласованные APT clean и journal vacuum уже выполнены; повторять без
  нового измерения незачем. Активные journal не обнулять.
- Build cache: перед согласованием повторить оценку private/shared.
  316.8 MB shared не означают 316.8 MB физически освобождаемого места.
- Не использовать system prune, volume prune, down -v и массовое удаление
  images/containers. Остановленные club_bot containers и связанные данные сохранить.
- Не удалять uploads/media, БД, backups, volumes и Docker JSON logs.
  Настройка ротации логов требует отдельного плана пересоздания сервисов.
- После согласованной очистки повторить df, docker system df и статус сервисов.

Фактический выигрыш — около 336 MiB, не несколько GiB. Очистка не решила
недостаточный запас RAM и почти заполненный swap.

## Выбор окружения

Для текущих 1 GiB RAM/10 GiB диска постоянный второй полный стек не рекомендован:
дополнительные PostgreSQL, FastAPI, Next.js и Nginx конкурируют с ботами за
память, диск и CPU. Текущий низкий CPU не доказывает запас на пиковую нагрузку.

Предпочтительно отдельное staging-окружение либо увеличение VPS. Начальная
инженерная оценка для общего сервера: 2 vCPU, 4 GiB RAM и 30–40 GiB диска;
это не измеренная гарантия ёмкости и требует проверки под нагрузкой.
Для первого просмотра возможна временная демонстрация на локальном компьютере
с синтетическими событиями через приватный доступ. Изменять сервер ботов для неё
не требуется. Внешний туннель/хостинг автоматически не создаётся.

## План staging под существующим Caddy после ревью и согласования

1. Утвердить окружение, адрес предпросмотра и приватный доступ (VPN либо Basic
   Auth для всего staging, включая `/api`). Оставить SITE_URL пустым/noindex;
   robots не заменяет защиту доступа. Не использовать реальные данные ботов.
2. Собирать linux/amd64 images FastAPI, standalone Next.js и Nginx+CRA вне VPS
   в CI/на отдельной машине. Переносить только проверенные images с фиксированными
   digest. PR-13 images не публикует и deploy не запускает.
3. Создать отдельный Compose project с уникальными network, новой пустой БД
   PostgreSQL 17, отдельными volume/uploads/secrets и ограничениями ресурсов.
   Не подключать к базам, media, Redis и backend сетям «Харизмы».
   Миграции 0001–0003 применять только к новой staging-БД. PR-8 BLOCKED,
   PR-9 не выполнен; демонстрация не подтверждает готовность timezone редактора.
4. Сначала запустить закрытый стек: наружу не публиковать backend/DB/public.
   Проверить health, память, диск и работу ботов до подключения ingress.
5. Caddy сейчас находится в двух сетях ботов; `127.0.0.1` внутри него не указывает
   на VPS. Нужна отдельная ingress-сеть только Caddy ↔ staging Nginx. Подключение
   Caddy и изменение Caddyfile — реальные изменения production и требуют
   отдельного согласования. Существующие webhook/media/default routes сохранить.
   Не запускать второй процесс на 80/443 и не пересоздавать ботов.
6. Перед reload проверить полную копию Caddyfile через `caddy validate`,
   сохранить исходную конфигурацию для точного отката, затем применить reload.
   Пример только будущего отдельного site block (не готовая конфигурация):

   ```caddyfile
   APPROVED_STAGING_HOST {
       # Здесь должна быть утверждённая защита всего staging.
       reverse_proxy afisha-staging-nginx:8080
   }
   ```

7. При Caddy → Nginx появляется второй proxy-hop. Текущий Nginx перезаписывает
   XFF на remote_addr, а scheme на HTTP: все клиенты будут видны как Caddy.
   До доступа нескольких редакторов отдельно подготовить и проверить exact-IP
   trust Caddy в Nginx и Nginx в Uvicorn, очистку forged forwarded headers,
   HTTPS redirects и независимость rate-limit buckets. Не включать wildcard trust.
8. Проверить HTTPS и закрытый доступ, `/`, `/events`, `/admin/login`, assets,
   API/login/logout/CRUD/uploads, приватность портов и отсутствие влияния на ботов.
   Затем измерить idle/peak RSS, swap-in/out, свободный диск и задержки.
   При недостатке ресурсов остановить только staging.
9. Откат: убрать только новый site block, validate/reload Caddy, остановить только
   staging project. Новую БД/uploads сохранить до отдельного решения об удалении.

Ни Caddy config, ни сети production в этой задаче не изменялись. Без выбранного
адреса/защиты, независимого review PR-13 и подтверждения ресурсов deploy заблокирован.
