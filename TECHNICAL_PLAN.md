## 2. Данные и семантика datetime — миграция заблокирована

Проверка в режиме чтения выполнена в пределах доступного: PostgreSQL недоступен, файловых БД нет. **Семантику существующих naive datetime установить нельзя.** Миграцию в `timestamptz` не выполнять.

Безопасные варианты (выбрать после появления данных):
1. **БД пуста** (вероятно для нового запуска): просто сменить тип, старой семантики нет.
2. **Данные есть, источник известен:** владелец или автор подтверждает, в какой зоне вводились даты. Миграция на копии, сверка 10–20 записей глазами, затем применение.
3. **Данные есть, источник неизвестен:** не конвертировать. Экспортировать, сверить с первоисточниками и пересоздать или перепроверить записи редактором. Колонку оставить naive, пока не выяснено.
4. **Смешанные данные:** конвертировать только подтверждённые партии (по `creator_id` или периоду), остальные пометить как неподтверждённые (не публиковать).

Что можно делать до этого: исправление диапазона дат (§4.1) работает на naive-колонке и от семантики не зависит.

## 4. Технические решения

### 4.1 Диапазон дат (A)
Вход `date_from`, `date_to`: календарные даты `YYYY-MM-DD`, обе включительно. Datetime в этих параметрах отклонять с 400 (или документировать иной контракт).
- `start = date_from 00:00` в Asia/Novosibirsk.
- `end = (date_to + 1 день) 00:00` в Asia/Novosibirsk.
- Запрос: `datetime >= start AND datetime < end`, обе границы переводятся в UTC после T6. **До T6** колонка naive, сравниваем naive-границы без конвертации: результат не зависит от зоны.
- Один день: `from = to = 2026-11-12` → `[2026-11-12 00:00, 2026-11-13 00:00)` по Новосибирску, в UTC `[2026-11-11T17:00Z, 2026-11-12T17:00Z)`.
- Неверная дата или `from > to` → 400, а не тихое отключение фильтра (сейчас `event_service.py` логирует и отключает).
- Серверные «сегодня/выходные» считать от `now` в Asia/Novosibirsk, не от `datetime.now()` хоста.
- Тесты: 00:00 и 23:59:59 выбранного дня входят, 00:00 следующего не входит; диапазон в несколько дней; один день; невалидный ввод; перевод через границу года.

### 4.2 Время в админке (B)
- Поле ввода — `datetime-local` строка без зоны. Интерпретировать её **только** как время Asia/Novosibirsk через `date-fns-tz` (`fromZonedTime(str, 'Asia/Novosibirsk')`); отображать `formatInTimeZone(iso, 'Asia/Novosibirsk', 'yyyy-MM-dd\'T\'HH:mm')`. Не использовать `new Date(str)` и `toISOString().slice(0,16)`.
- Тесты запускать с `TZ=Asia/Novosibirsk`, `TZ=UTC`, `TZ=America/Los_Angeles`, `TZ=Europe/Moscow`: round-trip «открыть и сохранить без изменений» не меняет момент времени.
- В CRA тестов сейчас нет: нужна настройка Jest (`process.env.TZ` в скрипте).

### 4.3 Отмена и жизненный цикл (C)
Два независимых поля:
- `publication_status`: `draft | published | archived` — редакционное состояние.
- `event_status`: `scheduled | cancelled | postponed` — состояние самого мероприятия. Перенос на известную дату — это `scheduled` с новым `datetime` (и, при желании, сохранённой прежней датой); `postponed` — перенос без даты.

Публичное поведение:
- `draft` и `archived`: не в каталоге, не в sitemap, страница отдаёт 404 (draft никогда не публиковался) либо 410/404 для archived — выбрать при реализации.
- `published` + `cancelled`/`postponed`: страница **доступна**, с заметным уведомлением; `robots` — index; schema.org `eventStatus` = `EventCancelled`/`EventPostponed`; в каталоге помечено или вынесено отдельно; в sitemap остаётся.
- Прошедшие `published`: остаются доступными по ссылке; в будущей выдаче не показываются.

Требует утверждения владельца (список R6, §8). `D-019` сейчас перечисляет `draft/published/cancelled` одним полем; решение нужно уточнить в `DECISIONS.md` после согласования.

### 4.4 API для Next.js (D)
- `INTERNAL_API_URL=http://backend:8039` — **серверный** URL (runtime-переменная, без префикса `NEXT_PUBLIC_`), для `fetch` в серверных компонентах, sitemap, route handlers. Контейнеры в одной compose-сети; backend слушает 8039.
- `NEXT_PUBLIC_API_BASE=/api` — только для кода в браузере. `NEXT_PUBLIC_*` вшивается при сборке.
- `SITE_URL` — абсолютный адрес сайта для canonical, Open Graph и sitemap; **значение не задано, пока домен не утверждён**.
- Проверки: из контейнера Next.js `GET http://backend:8039/health`; через Nginx `GET /api/health`; запрос серверного рендера не должен идти через внешний домен.
- Nginx сохраняет текущее поведение `proxy_pass http://…/` (префикс `/api` срезается).

### 4.5 Черновики, валидация, `verified_at` (E)
- Новые колонки `organizer_id, event_url, source, verified_at, publication_status, event_status` — nullable или со значениями по умолчанию (`publication_status='draft'`, `event_status='scheduled'`). Никаких безусловных `NOT NULL`, которые ломают существующие записи.
- Существующие записи получают `publication_status='draft'` (не публиковать автоматически) и `verified_at=NULL`.
- `verified_at` ставится **только явным действием редактора** («проверено»), с кем и когда; не при создании и не при любой правке.
- Обязательные для публикации (D-019): название, дата с зоной, место или онлайн-ссылка, организатор, `event_url`, `source`, `verified_at`. Проверка на backend (а не на frontend) при переходе в `published` **и при каждом изменении уже опубликованного события**: если после правки поля перестали удовлетворять требованиям, правка отклоняется.
- Цена: три состояния (бесплатно / известная / не указана). Текущий `price Integer NULL` неоднозначен (`NULL` и `0`): отдельное поле `price_type` и решение для старых строк — не угадывать.
- Для будущего импорта: `source` хранится как URL первоисточника; отдельную таблицу источников не создавать до появления импорта (D-016).

### 4.6 Безопасность HTML и ссылок (F)
- Описание — обычный текст (React экранирует) либо Markdown через renderer без сырого HTML. `dangerouslySetInnerHTML` не использовать.
- `event_url`, `source`, `website`: только `http`/`https`; ссылки наружу — `rel="noopener noreferrer nofollow"`, `target="_blank"`.
- JSON-LD: после `JSON.stringify` заменять символ `<` на последовательность `\u003c`, чтобы данные события не могли закрыть тег `<script>`.
- В текущем frontend проверить поиском использование `dangerouslySetInnerHTML` и `href` из данных (не выполнялось).

### 4.7 Версии (G)

Версию зафиксировать при создании проекта и проверить совместимость с переиспользуемыми компонентами (`lucide-react`, `react-hook-form`, `react-hot-toast`, календари). Поведение кеширования в 16.x сверить с документацией (модель кеша менялась между версиями), не переносить допущения из 14/15.

## 6. Инфраструктура и маршрутизация

- Схема: один origin; `/` → Next.js, `/admin` → CRA (собран с `PUBLIC_URL=/admin`, `basename="/admin"`), `/api/` → FastAPI, `/uploads/` или текущий `/static/uploads/` → файлы. **Разрешить конфликт `/static`:** CRA под `/admin/static/…`, backend `/static/uploads/` не трогается; Next.js использует `/_next/`.
- Backend и PostgreSQL недоступны снаружи (порты на `127.0.0.1` в compose — оставить; в production не публиковать).
- Uploads: том для `app/static/uploads` общий для backend и Nginx; путь в Nginx сейчас абсолютный (`/var/www/alexon/…`) — привести к реальному пути на сервере; бэкап включить в T17.
- **Обязательное условие публичного запуска — доверенный reverse proxy (проверено на реальном Nginx и Uvicorn 0.24.0, см. D-011):**
  1. Uvicorn: `--proxy-headers --forwarded-allow-ips=<адрес Nginx>`; только адрес известного прокси, никогда `*`; значение берётся из конфигурации, не зашито. До настройки остаётся `--no-proxy-headers`, но тогда все клиенты за Nginx делят один бакет источника (тест: 31 неудача одного клиента дала 429 другому).
  2. Nginx перезаписывает заголовок: `proxy_set_header X-Forwarded-For $remote_addr;`. Текущий `deploy/nginx/afisha.conf` использует `$proxy_add_x_forwarded_for` (дописывает) — заменить.
  3. Прямое обращение к backend не позволяет подделать IP: недоверенный пир игнорируется (проверено, три поддельных адреса дали один бакет). Порт backend недоступен из интернета.
  4. У нескольких клиентов независимые бакеты источника (проверено на двух клиентах).
  5. Если перед Nginx появится CDN или балансировщик — настроить `real_ip` в Nginx, иначе адрес снова общий.
  Compose-`command` сейчас зашивает `--no-proxy-headers`: сделать настраиваемым (PR-12, T8). Требование не откладывается за публичный запуск.
- **Защита входа администратора (известное ограничение D-011):** 5 неудач на аккаунт за 15 минут позволяют заблокировать чужой вход. Перед публичным запуском нужна дополнительная защита (allowlist IP, Basic Auth, VPN или MFA). Способ не выбран: решение владельца, требует согласования способа доступа редактора.
- ISR/кеш: после изменения события backend вызывает защищённый секретом route handler Next.js по внутреннему URL; **ошибка вызова не должна ломать сохранение** — запасной вариант: короткий `revalidate` по времени. Проверять, что опубликованное изменение (в т.ч. отмена) появляется на странице; при нескольких экземплярах Next.js кеш общий — отдельное решение.
- Production-домен: не утверждён. Не использовать `afisha-nsk.ru` и не копировать `afisha.lalexonl.ru` в новые конфиги без решения владельца.

## 7. Аналитика (D-017)

Метрики: уникальные и возвращающиеся посетители, просмотры каталога и карточек, переходы к внешней регистрации, источники трафика.

**Plausible Community Edition** (предварительный выбор владельца). По README репозитория `plausible/community-edition` (тег v3.0.1, прочитан): нужен ClickHouse, процессор с SSE 4.2 или NEON, **рекомендуется не менее 2 ГБ RAM** для ClickHouse и Plausible. Это отдельно от backend, PostgreSQL и Next.js. Использовать официальную конфигурацию, не упрощённый compose. Нагрузку на сервер оценить нельзя: **сервер не выбран**.

| --- | --- | --- |
| Plausible CE (официальный compose) | Готовые отчёты, события исходящих ссылок | ClickHouse и ≥2 ГБ RAM сверх основного стека; отдельное сопровождение и обновления |
| Лёгкий вариант: серверный счётчик в нашей БД (просмотры и переходы), без cookies | Минимум инфраструктуры, под контролем | Своя реализация; «возвращающиеся» без постоянного идентификатора считать нельзя; расширяется в самостоятельный модуль |
| Внешний хостинг аналитики | Ничего не разворачиваем | Данные уходят третьей стороне — отдельная проверка |

Рекомендация: **решение не принимать до выбора сервера.** Если на сервере есть запас ≥2 ГБ RAM сверх основного стека, берём Plausible CE по официальной схеме. Иначе — лёгкий вариант, оформленный как маленький модуль (две таблицы, два эндпоинта). События перехода к регистрации: кастомное событие Plausible при клике или серверная запись; точный способ проверяется на реальном сайте. О соответствии требованиям приватности (включая российское законодательство о персональных данных) нельзя заявлять без проверки конкретной конфигурации: IP-адреса, cookies, хранение.

## 9. Оценки (предварительные)

Допущения: один разработчик на полной занятости, знакомый со стеком; PostgreSQL и Docker доступны; сервер к концу работ выбран; данные для T6 подтверждены; stash проходит ревью без существенной переделки.
