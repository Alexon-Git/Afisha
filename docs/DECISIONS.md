## D-001 — Рабочая основа репозитория
- **Статус:** Принято.
- **Решение:** реанимировать `Alexon-Git/Afisha`, а не создавать новый
  проект. `master` — основная ветка; `main` — историческая резервная.
- **Причина:** уже существуют API, каталог, календарь, админка, Docker.
- **Следствие:** миграции и рефакторинг инкрементально, с тестами.

## D-002 — Вертикаль продукта
- **Статус:** Принято как стратегическое направление.
- **Решение:** фокус на деловых мероприятиях **Новосибирска**,
  аудитории событий, прогнозной посещаемости, организаторах
  и возможностях партнёрства.
- **Следствие:** не распыляться на общую афишу концертов/кино.

## D-003 — Безопасное управление схемой БД
- **Статус:** Принято и реализовано в master.
- **Решение:** схема развивается через Alembic. Старт FastAPI
  не добавляет колонки. Для старой БД обязательны бэкап и сверка
  схемы на изолированной копии; начальная миграция не перезаписывает
  существующие таблицы.
- **Источник:** `backend/MIGRATIONS.md`.

## D-004 — Публичная регистрация
- **Статус:** Принято временно.
- **Решение:** `POST /auth/register` доступен только администратору,
  пока не спроектированы пользовательские роли/регистрация и антиспам.
- **Следствие:** самостоятельная регистрация пользователей не часть
  текущей рабочей реализации.

## D-005 — Платёжная модель MVP
- **Статус:** Предложено.
- **Решение:** внешние ссылки на регистрацию/оплату организатора,
  без собственного ticketing и acquiring.
- **Причина:** уменьшение scope и юридической сложности.
- **До принятия:** подтвердить UX и модель монетизации.

## D-006 — Публичный frontend
- **Статус:** Открыто.
- **Варианты:** оставить React SPA с отдельными решениями SEO;
  частично/полностью перевести публичный frontend на Next.js.
- **Критерии:** SEO, скорость до MVP, повторное использование
  существующих компонентов, стоимость поддержки.
- **Не делать:** не мигрировать Next.js без решения владельцев.

## D-007 — Данные посещаемости
- **Статус:** Предложено для утверждения.
- **Решение:** отдельно хранить вместимость, прогноз, регистрации
  и факт; явно обозначать источник и неопределённость.
- **Не делать:** показывать прогноз как достоверное число пришедших людей.

## D-008 — Управление рекламой
- **Статус:** Предложено.
- **Решение:** MVP: ручное создание рекламных кампаний редактором,
  управляемые слоты и базовые метрики.
- **Не делать:** автоматическая продажа без подтверждённой модели
  и правовой проверки рекламных требований.

## D-009 — Контент и партнёрства
- **Статус:** Принято как рабочий принцип.
- **Решение:** использовать реальные и проверяемые сведения;
  «Харизма», «Мой бизнес» и другие бизнес-клубы — потенциальные
  источники, не подтверждённые интеграции.
- **Следствие:** контент нельзя маскировать под официальное
  партнёрство или копировать без разрешения.

## D-010 — AI-агенты и gstack
- **Статус:** Принято для документации / открыто для установки.
- **Решение:** хранить контекст работы в репозитории через `AGENTS.md`,
  `CLAUDE.md`, `docs/`. gstack рассматривается как
  инструмент ревью, безопасности и QA.
- **Следствие:** сама документация не означает, что gstack уже
  установлен или выполнен. Внешние инструменты требуют проверки
  выполняемых команд и явно оговоренных разрешений.

## D-011 — Общие счётчики входа и безопасная идентификация источника
- **Дата:** 2026-11-12. **Статус:** Принято и реализовано. PR #16 влит в `master`
  (merge-коммит `666696e`; коммиты `b9cba12`, `138ca5e`); CI Pull Request и CI
  `master` после merge — success.
- **Основание:** защита POST `/auth/login` для нескольких процессов без доверия
  непроверенным forwarded-заголовкам (Engineering Review A1, A2).
- **Решение:** существующая SQL-БД, таблица `login_attempts`, Alembic
  `0002_login_attempts`. Redis и новые зависимости не нужны. SQLite — локально,
  PostgreSQL — production.
- **Механизм:** транзакционный UPSERT резервирует бюджеты источника и точного
  username до проверки пароля; конкурентные запросы не превышают лимит. Успех
  возвращает только свой слот, прежние неудачи остаются до конца окна. Отказ
  одного бюджета откатывает оба; 429 окно не продлевает.
- **Параметры:** 5 на аккаунт и 30 на источник за 900 с (`LOGIN_ACCOUNT_LIMIT`,
  `LOGIN_SOURCE_LIMIT`, `LOGIN_WINDOW_SECONDS`). Всем workers нужны общие БД и
  `SECRET_KEY`; при нескольких хостах — синхронизация часов.
- **Отказ хранилища:** fail closed — 503 с `Retry-After: 60`, токен не выдаётся.
  429 возвращает оставшееся время. Без миграции login недоступен.
- **Приватность:** ключи HMAC-SHA256, без открытых имён и IP; пароли и токены не
  попадают ни в счётчики, ни в логи.
- **Proxy:** wildcard `ProxyHeadersMiddleware` удалён, Uvicorn запускается с
  `--no-proxy-headers` (Dockerfile, compose `command`, `start.py`).
- **Проверено (2026-11-12):**
  - SQLite: полный набор, 68 тестов прошли (Python 3.11).
  - PostgreSQL 17: `upgrade`/`downgrade -1`/`upgrade` прошли; 50 параллельных
    попыток по одному аккаунту пропустили ровно 5, 80 по одному источнику — ровно
    30, 120 смешанных — без ошибок и дедлоков; недоступная БД — fail closed.
  - Docker Compose (изолированный проект): образ собирается и запускается,
    `command` из compose переопределяет `CMD` и сохраняет `--no-proxy-headers`,
    миграции применяются, после 5 неудач — 429 с `Retry-After`, поддельные
    `X-Forwarded-For`, `X-Real-IP`, `Forwarded` источник не меняют.
  - Реальный Nginx перед backend с `--no-proxy-headers`: **проблема общего
    источника** — 31 неудачный вход одного клиента привёл к 429 для другого
    клиента (легитимный вход админа).
  - Безопасный вариант проверен на Nginx и Uvicorn 0.24.0: `--proxy-headers
    --forwarded-allow-ips=<адрес Nginx>` и `proxy_set_header X-Forwarded-For
    $remote_addr;`. Два клиента получили независимые бакеты, прямое обращение
    недоверенного пира с поддельным заголовком даёт один бакет.
  - Не проверено: копия реальной старой БД (данных нет); production-конфигурация.
- **Обязательное условие публичного запуска:** настроить production reverse proxy
  по проверенной схеме (см. `TECHNICAL_PLAN.md` §6 и `RELEASE_CHECKLIST.md` §1).
  Откладывать за пределы запуска нельзя.
- **Известное ограничение:** 5 попыток на аккаунт за 15 минут позволяют любому, кто
  достучится до `/auth/login`, блокировать вход известного пользователя на окно.
  Политика сохранена; перед публичным запуском нужна дополнительная защита входа
  администратора. Способ доступа редактора (allowlist IP, Basic Auth, VPN, MFA)
  не выбран и требует согласования.

## D-012 — Целевая аудитория MVP
- **Статус:** Принято.
- **Дата:** 2026-11-12
- **Решение:** первичный сегмент — **действующие предприниматели Новосибирска**, которые уже посещают деловые мероприятия и выбирают следующую встречу ради обмена опытом, поиска подрядчиков или деловых контактов.
- **Причина:** узкий проверяемый сегмент с понятным критерием успеха (выбор подходящего события и переход к регистрации); проще собрать обратную связь и измерить повторное использование.
- **Следствие:** UX, контент и фильтры оптимизируются для этой аудитории; расширение на студентов, начинающих предпринимателей и профессиональных посетителей конференций откладывается до подтверждения базового сценария.
- **Связь:** D-002 (фокус на деловых мероприятиях Новосибирска), Product Review O-1.

## D-013 — Упрощение функционального scope MVP
- **Статус:** Принято.
- **Дата:** 2026-11-12
- **Решение:** отложить из первого MVP сложные модули; фокус на главном сценарии (помочь выбрать подходящее событие):
  - **F-09 (реклама):** управление рекламными кампаниями, слоты, биллинг, кабинет рекламодателя — полностью откладываются до проверки спроса и ручной коммерческой модели.
  - **F-06 (посещаемость):** прогнозная модель, attendance-аналитика, гарантии посещаемости — остаётся необязательное поле с источником, если данные доступны.
  - **F-02 (фильтры):** многомерные фильтры по ЦА/цене/формату/месту упрощаются до даты/диапазона и базовых категорий.
  - **F-05 (аудитория):** сложная система тегов и фильтры по аудитории заменяются коротким редакционным описанием "для кого" с указанием источника.
  - **F-07 (организаторы):** публичный каталог организаторов и полноценные профили откладываются; сохраняется полноценная сущность Organizer и связь мероприятий с организаторами на уровне модели данных согласно принятой архитектуре; в публичной карточке события остаётся название организатора и проверенная ссылка/контакт.
  - **F-08 (партнёрство):** база лидов, CRM, обработка заявок откладываются; остаётся контакт организатора для делового запроса, если тот согласен его публиковать.
  - **F-10 (админка):** формальная многоэтапная модерация заменяется базовыми операциями управления мероприятиями и их публикацией (создать, проверить, опубликовать, скрыть, архивировать).
- **Причина:** фокус на проверке главной гипотезы; нет подтверждённых источников данных посещаемости и партнёрских интеграций (D-009).
- **Следствие:** существующий функционал сохраняется без удаления; расширение возвращается по результатам проверки спроса и после появления подтверждённых источников данных; не удаляем уже реализованный функционал без отдельного технического обоснования.
- **Связь:** D-005 (внешние ссылки на регистрацию), D-007 (данные посещаемости), D-008 (ручное управление рекламой), Product Review O-6.

## D-014 — Публичный запуск и SEO-требования
- **Статус:** Принято.
- **Дата:** 2026-11-12
- **Решение:** запуск **публичного каталога с первого релиза** с закладкой SEO-требований в архитектуру. Не проводим закрытый пилот как обязательный этап перед публичным запуском.
- **Обязательные требования:**
  1. Публичный каталог доступен без авторизации.
  2. Постоянные URL для страниц мероприятий (`/events/:id` или `/events/:slug`).
  3. Индексируемые HTML-страницы мероприятий.
  4. SEO-метаданные (title, description), Open Graph теги для корректного превью в соцсетях и мессенджерах.
  5. Генерация sitemap.xml.
  6. Первоначальное наполнение контента вручную через административную панель.
  7. Первоначальное привлечение через предпринимательские сообщества, Telegram и личные контакты; SEO — стратегический канал привлечения.
- **Архитектурное решение:** SEO закладывается в архитектуру с первого релиза. **Next.js пока не утверждён.** Решение об архитектуре frontend принимается отдельно после сравнения допустимых способов обеспечения SEO с учётом:
  - Существующей React SPA кодовой базы и возможности переиспользования компонентов.
  - Стоимости миграции маршрутов, data fetching, server/client границ, кеша.
  - Альтернативных решений (генерация статичных страниц, SSR через FastAPI, гибридный подход).
  - Требований к хостингу и эксплуатации (self-hosting, обновление контента, кеширование).
- **Следствие:** критические блокеры публичного запуска из Engineering Review требуют приоритетного исправления; решение по frontend рендерингу принимается после анализа вариантов и их стоимости; архитектурные решения R1-R5 требуют отдельного утверждения.
- **Связь:** D-006 (публичный frontend — остаётся открытым для архитектурного решения), Engineering Review R1 (обязательность публичных HTML/OG страниц), Product Review O-7.

## D-015 — Ответственный за контент и редакционный процесс
- **Статус:** Принято.
- **Дата:** 2026-11-12
- **Решение:** отдельный сотрудник команды несёт персональную ответственность за актуальность каталога; плановая загрузка 5-10 часов в неделю.
- **Организация процесса:**
  1. Сотрудник собирает анонсы от организаторов и из разрешённых публичных источников.
  2. Проверяет название, дату, время, место, формат, цену и ссылку регистрации.
  3. Заполняет и обновляет мероприятия через административную панель.
  4. Отслеживает переносы, отмены и дубликаты мероприятий.
  5. Сохраняет источник информации и дату последней проверки.
  6. Регулярно проверяет ближайшие мероприятия и архивирует прошедшие.
  7. После первых двух недель работы оценивается фактическая трудоёмкость; при необходимости ресурс корректируется.
- **Причина:** регулярное наполнение и проверка актуальности контента — необходимое условие доверия к каталогу; один ответственный упрощает координацию и контроль качества.
- **Следствие:** конкретный сотрудник назначается до публичного запуска; дополнительные инструменты управления редакцией не требуются в MVP; сохраняется стратегия публичного запуска (D-014).
- **Связь:** D-009 (проверяемые сведения и источники), D-014 (ручное наполнение через админку), Product Review O-2.

## D-016 — Источники мероприятий и расширяемость системы сбора
- **Статус:** Принято.
- **Дата:** 2026-11-12
- **Решение:** агрегация мероприятий из различных открытых источников (вариант A). Концепция «Бизнес Афиши» — единый публичный агрегатор деловых мероприятий Новосибирска. Команда самостоятельно находит анонсы на сайтах организаторов, бизнес-клубов, площадок, в публичных Telegram-каналах и других доступных источниках, обрабатывает информацию и размещает мероприятия в собственном каталоге.
- **Основные принципы:**
  1. Прямые соглашения с организаторами не являются обязательным условием запуска.
  2. На старте — открытые источники и ручная редакторская обработка через административную панель.
  3. Для каждого мероприятия обязательно сохраняем ссылку на первоисточник и дату проверки.
  4. Проверяем актуальность даты, времени, места, стоимости и регистрации.
  5. Исключаем дубли, отслеживаем переносы и отмены.
  6. Публикуем самостоятельно составленные описания на основе проверенных фактических сведений; не копируем автоматически чужие тексты, изображения и другие охраняемые материалы без необходимых прав.
  7. Для регистрации пользователь переходит на официальный ресурс организатора.
  8. Сотрудничество с организаторами может стать дополнительным каналом получения информации в будущем, но не является зависимостью публичного запуска.
- **Архитектурная расширяемость:** на этапе MVP мероприятия добавляются вручную; в дальнейшем планируется полуавтоматический сбор с обязательной редакторской проверкой перед публикацией. Архитектурные требования предусматривают (не реализуются в MVP):
  - Хранение первоисточника и времени последней проверки.
  - Возможность подключения разных источников данных.
  - Возможность обнаружения дубликатов.
  - Возможность обновления существующих мероприятий при изменении информации.
  - Разделение получения информации, редакторской проверки и публикации.
- **Причина:** команда не зависит от получения регулярных анонсов от 3-5 партнёров; ценность продукта — объединение разрозненной информации в удобный единый каталог; актуальность и достоверность данных обеспечиваются редакторской проверкой.
- **Следствие:** не реализуем в MVP парсеры, автоматические интеграции или инфраструктуру импорта; не усложняем MVP преждевременными абстракциями; архитектура должна позволять в дальнейшем подключать новые источники данных.
- **Связь:** D-009 (проверяемые сведения, потенциальные источники не подтверждённые интеграции), D-015 (редактор собирает анонсы из разрешённых публичных источников), Product Review O-3.

## D-017 — Проверка спроса и метрики оценки
- **Статус:** Принято.
- **Дата:** 2026-11-12
- **Решение:** публичный запуск с восьминедельным периодом оценки после релиза. По результатам периода принимается решение о дальнейшем развитии.
- **Основные метрики:**
  - Уникальные посетители из целевой аудитории (D-012: действующие предприниматели Новосибирска).
  - Просмотры карточек мероприятий.
  - Переходы к внешней регистрации.
  - Повторные посещения.
  - Количество актуальных мероприятий в каталоге.
  - Регулярность обновления каталога.
- **Причина:** восемь недель достаточны для первичной оценки полезности продукта; произвольные количественные пороги не устанавливаются как автоматические критерии закрытия проекта; качественная оценка вовлечённости важнее абсолютных чисел на старте.
- **Следствие:** точный бюджет продвижения и количественные KPI остаются открытыми параметрами; аналитика фиксирует поведение пользователей для принятия обоснованного решения; наполнение каталога и редакторский процесс проверяются на практике (D-015, D-016).
- **Связь:** D-012 (целевая аудитория), D-014 (публичный запуск), D-015 (редакционный процесс), D-016 (источники контента), Product Review O-4.

## D-018 — Модель монетизации MVP
- **Статус:** Принято.
- **Дата:** 2026-11-12
- **Решение:** параллельная коммерческая работа во время разработки MVP; основная модель B2B — платное продвижение мероприятий, специальные размещения и партнёрские предложения организаторам; посетителям доступ бесплатный.
- **Коммерческая стратегия:**
  - Допускаются ручные коммерческие предложения и договорённости с организаторами до и после публичного запуска.
  - Не обещаем неподтверждённые охваты, регистрации и посещаемость.
  - Автоматизированный рекламный кабинет, платёжный биллинг и сложная рекламная аналитика откладываются (D-013 отложил F-09).
  - Первые ручные продажи проверяют готовность платить и помогают сформировать коммерческое предложение.
- **Причина:** проверка коммерческой модели параллельно с продуктовой; ручные сделки не требуют разработки рекламного модуля; первые договорённости помогают понять ценообразование и востребованность услуг.
- **Следствие:** ручное управление размещением через административную панель; коммерческие условия согласуются индивидуально; после проверки спроса можно стандартизировать предложения и автоматизировать процесс.
- **Связь:** D-005 (внешние ссылки на регистрацию), D-008 (ручное управление рекламой), D-013 (F-09 отложена), Product Review O-5.

## D-019 — Качество данных о мероприятии
- **Статус:** Принято.
- **Дата:** 2026-11-12
- **Решение:** проверенный минимум сведений о мероприятии (вариант B). Каждое опубликованное мероприятие содержит достоверные проверенные данные с указанием источника и даты проверки.
- **Обязательные данные:**
  - Название мероприятия.
  - Дата и время с указанием временной зоны (Asia/Novosibirsk).
  - Формат и место проведения либо онлайн-ссылка.
  - Организатор (название и контакт, связь Event → Organizer).
  - Ссылка на мероприятие или регистрацию у организатора.
  - Первоисточник (откуда взяты сведения).
  - Дата последней проверки актуальности.
  - Статус публикации (draft/published/cancelled).
- **Необязательные данные (заполняются если доступны):**
  - Цена (три состояния: бесплатно, известная стоимость, не указана).
  - Изображение.
  - Редакторское описание.
  - Короткое пояснение "для кого" (D-013 упростил теги).
  - Примерная посещаемость (если источник известен).
- **Архитектурные требования:** модель Event должна поддерживать:
  - Связь Event → Organizer (может быть NULL на старте, архитектура предусматривает).
  - Поля: `source` (обязательное), `verified_at` (обязательное), `publication_status` (draft/published/cancelled).
  - Возможность изменения даты, отмены мероприятия и предотвращения дублей.
- **Причина:** прозрачность источников и актуальность данных — конкурентное преимущество (Product Review §4); обязательная проверка снижает риск публикации устаревшей или неверной информации; статусы публикации позволяют работать с черновиками и отменами.
- **Следствие:** Engineering Review A5 требует добавления модели Organizer и полей source/verified_at/publication_status до публичного запуска; редакторский процесс включает проверку обязательных полей (D-015).
- **Связь:** D-013 (упрощение F-05, F-06), D-015 (редакторский процесс), D-016 (хранение первоисточника), Engineering Review A5, Product Review O-8.
- **Уточнение 2026-11-12 (технический план v2.1):** «обязательные» поля относятся к
  **публикации**, а не к черновику. Черновик может быть неполным; в БД новые поля
  nullable. Проверка выполняется на backend при публикации и при каждой правке
  уже опубликованного события. `verified_at` ставится только явным действием
  редактора, а не при создании записи. Формулировка «статус публикации
  (draft/published/cancelled)» и перечень статусов **не окончательны**:
  предложено разделить статус публикации и статус самого мероприятия
  (отмена, перенос); решение ждёт владельца (R6).
