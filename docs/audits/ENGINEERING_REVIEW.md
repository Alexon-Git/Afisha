## 2. Сильные стороны реализации

- **Разделение API, сервисов и данных уже есть.** Сохранять
  [routers/events.py](../../backend/app/routers/events.py#L18),
  [dependencies.py](../../backend/app/dependencies.py), `EventService` и Alembic,
  а не переносить бизнес-логику в новый frontend.
- **Права записи проверяются сервером.** Create/update/delete/upload событий,
  изменение категорий и регистрация требуют `get_current_admin_user`;
  [auth.py:86](../../backend/app/auth/auth.py#L86) проверяет `is_admin`.
  Клиентский ProtectedRoute не является единственной защитой API.
- **Ответы пользователя типизированы.**
  [schemas/user.py](../../backend/app/schemas/user.py#L23) не включает password_hash.
  Публичный список пользователей в просмотренных роутерах не обнаружен.
- **Нет runtime-изменения схемы в main.py.** Начальная миграция отказывается
  молча менять старую неверсионированную БД:
  [0001_initial.py:19](../../backend/alembic/versions/0001_initial.py#L19).
- **Безопасная загрузка из PR #15 — переиспользуемая готовая основа.**
  [event_service.py:153](../../backend/app/services/event_service.py#L153)
  ограничивает чтение до декодирования, затем проверяет/перекодирует изображение.
  В [тестах](../../backend/tests/test_image_upload.py#L105) есть повреждения,
  поддельные типы, ошибки декодера и EXIF-ориентация.
- **Базовые механизмы роста присутствуют.** `limit` ограничен 100, список
  использует `joinedload(Event.category)`; утверждать здесь ORM N+1 для категорий
  было бы неверно. SQL-фильтры строятся выражениями SQLAlchemy, не конкатенацией
  пользовательских строк.
- **Bootstrap не повышает чужие права автоматически и не меняет существующий
  пароль:** [create_admin.py:13](../../backend/create_admin.py#L13). Это безопасное
  поведение, но оно не заменяет процедуру ротации.

## 4. React SPA и Next.js для этого проекта

React как UI-библиотека не является ошибкой выбора. **CRA и React SPA — разные
решения**: переход с CRA на поддерживаемый bundler не даёт SSR/индексацию сам по
себе. React официально объявил CRA deprecated и рекомендует существующим
проектам framework либо другой build tool:
[React, Sunsetting Create React App](https://react.dev/blog/2025/02/14/sunsetting-create-react-app).

| Вариант | Польза здесь | Риски / стоимость |
| --- | --- | --- |
| Сохранить SPA для закрытого пилота | Максимум reuse карточек, форм, API и админки; статический frontend | Нужны общие исправления A/C; публичные SEO-страницы и OG текущая реализация не обеспечивает |
| SPA + отдельная генерация публичного HTML | Сохраняет большую часть UI; возможно без постоянного Node frontend | Появляется собственный процесс генерации/инвалидации и проверка свежести отмен/переносов. Это не бесплатное «добавить метатеги» |
| Next.js для публичных страниц, FastAPI остаётся API | Удобные маршруты, серверные metadata/OG и варианты server/static rendering; переиспользование React-компонентов | Перенос router/env/data fetching, server/client-границы, CSS и зависимости, обработка ошибок/404, кеш и публикация. Бизнес-логика остаётся в FastAPI |
| Переписать frontend и backend на Next.js | Единый язык части системы | Теряются проверенные Python-сервисы и миграционный путь; новая auth/data-логика и высокий риск регрессий. Обоснования не найдено |

Next.js поддерживает [серверные metadata и OG](https://nextjs.org/docs/app/getting-started/metadata-and-og-images),
но это не гарантирует ранжирование. При self-hosting надо учитывать
[кеш и координацию экземпляров](https://nextjs.org/docs/app/guides/self-hosting).
Статический export не требует постоянно работающего Node-сервера, однако
обновление опубликованных событий тогда зависит от генерации/выкладки.
Для SSR/ISR требуется соответствующий runtime и политика свежести. Не обещать
«без дополнительной эксплуатации» и не требовать Redis/Vercel автоматически.

**Рекомендация:** сохранить FastAPI + SQLAlchemy + PostgreSQL; сохранить
React-компоненты и клиентскую админку. Для ручного/закрытого пилота использовать
SPA после необходимых исправлений. Если постоянные индексируемые страницы и
корректное превью события обязательны именно к публичному MVP, предпочтителен
ограниченный переход публичной части на Next.js вместо собственной SSR-системы.
Владелец должен утвердить этот порог до переработки маршрутов. Нельзя выдавать
plain SPA без серверного HTML за выполнение F-04 и SEO-требований.

Оценка стоимости — относительная, не смета и не обещание сроков:

| Пакет | Состав | Относительная стоимость |
| --- | --- | --- |
| Сохранение SPA | API-origin/префикс, маршруты, состояния, regression build | Низкая для закрытого пилота; публичный HTML сюда не включён |
| Генерация HTML рядом со SPA | Источники данных, генератор, обновления и invalidation, ошибки/preview | Средняя; собственный процесс потребуется сопровождать |
| Узкая миграция Next.js | Public layout/routes → API/URL/env → metadata/404 → кеш/обновления → regression/deployment | Средняя/высокая; UI можно переиспользовать, перенос не сводится к установке пакета |
| Полная перепись | Новый frontend, API, auth, data access и эксплуатация | Высокая, не рекомендована |

Достоверную оценку в часах/деньгах сейчас дать нельзя: frontend build не проверен,
Node-хостинг и freshness-требования не выбраны. Сначала нужен ограниченный
проверочный перенос одной карточки без изменения API; он **не разрешён этим
аудитом**. В смету отдельно включать общие дефекты A/C — они существуют и без Next.js.

## 5. Рекомендации для архитектуры MVP

### Сохранить

- Один FastAPI backend, SQLAlchemy-сервисы и Alembic. PostgreSQL для production,
  SQLite для быстрых изолированных проверок с явно проверенным паритетом.
- Серверные admin-права; не заменять их ProtectedRoute/скрытием кнопок.
- Проверку изображений из PR #15, typed schemas, backend-пагинацию и eager loading.
- Существующие React-компоненты; не строить заново весь редакторский интерфейс.

### Изменить после утверждения

- Установить один контракт browser-origin/API-prefix/reverse proxy и разделение
  локального, тестового и production окружений. Прямой browser-доступ к старому
  production origin не должен быть неизменяемой константой.
- Установить точное время события: хранение, ввод, локальное отображение,
  календарные границы и перенос старых записей. Не мигрировать naive значения
  в UTC без понимания их прежнего смысла.
- Минимально добавить организатора, источник/проверку и публикационные состояния
  после утверждения MVP. Предпочтительно отношение Event → Organizer, а не
  копирование изменяемых контактов в каждую карточку; конкретная миграция не спроектирована.
- Для будущего публичного рендеринга FastAPI остаётся владельцем правил/БД.
  Frontend/Next получает данные через API и не создаёт второй независимый набор
  правил публикации, прав и валидации.

```text
Возможная целевая граница (не утверждена)
  публичная HTML-страница /events/<id-or-slug> → публичный API
  клиентский React-редактор                 → admin API
                                                   │
                      единые сервисы / правила / транзакции FastAPI
                                                   │
                                PostgreSQL + управляемые изображения
```

**Две формы публичной границы:** A — SPA с отдельной генерацией HTML;
B — Next.js как frontend к тому же FastAPI. B предпочтительнее при обязательном
server-rendered публичном MVP, поскольку не требует собственной системы
рендеринга и metadata. Это предложение, не одобренная новая граница.
Разделять фронтенд на два независимо поддерживаемых приложения необязательно:
в Next можно сохранить админские React-экраны клиентскими, но оценить перенос отдельно.

### Сбои и восстановление

```text
Выбор даты → запрос API → проверка ответа → показ результата
  ошибка/старый ответ → сейчас возможны старые карточки или пустые категории
  желаемое поведение → явная ошибка/пустота и защита от устаревшего ответа

  ошибка commit → запись осталась, файл уже отсутствует
  желаемая граница → согласованный жизненный цикл и безопасное удаление ресурса
```

production-инцидентов и не значит, что остальные риски несущественны.
